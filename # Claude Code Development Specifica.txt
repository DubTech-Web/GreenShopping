# Claude Code Development Specification

## AI-Powered Sustainable E-Commerce Platform — Green Software Engineering

You are the primary software engineer responsible for developing this project from start to finish.

Build a complete but deliberately simple **AI-Powered Sustainable E-Commerce Platform** whose primary academic purpose is to demonstrate **Green Software Engineering**.

The most important principle is:

> **Build only what is necessary, use the simplest technology that satisfies the requirement, minimize computational/resource consumption, and make the sustainability impact measurable.**

Do NOT over-engineer the system.

Do NOT add features merely because they are common in e-commerce applications.

Do NOT introduce microservices, unnecessary external APIs, complex AI models, unnecessary background workers, Redis, Kubernetes, message queues, or other infrastructure unless a requirement genuinely cannot be satisfied without them.

---

# 1. EXACT PROJECT REQUIREMENTS

The system must implement ONLY these functional requirements:

1. Customer registration and authentication
2. Product catalog
3. Shopping cart
4. Order processing
5. AI recommendation engine
6. Green delivery options
7. Carbon footprint estimator
8. Inventory management
9. Administrative dashboard
10. Sales and sustainability reports

Green software engineering requirements:

1. Eco-friendly delivery recommendations
2. Energy-efficient database operations
3. Optimized API calls
4. Sustainable hosting considerations
5. Carbon impact reporting

The project description is:

> Develop an e-commerce application that incorporates AI-driven product recommendations while promoting environmentally sustainable shopping practices. The system should estimate the environmental impact of deliveries, recommend eco-friendly alternatives, and optimize inventory management.

Everything you implement must be traceable to one of these requirements.

---

# 2. CORE DEVELOPMENT PRINCIPLE

Before writing significant code, analyze the requirements and create a small requirements-to-implementation matrix.

For every feature, identify:

* Requirement number
* User/system behavior
* Backend component
* Frontend component
* Database data required
* API endpoint required
* Tests required

Do not implement functionality that cannot be justified by a requirement.

If you believe an additional feature is necessary, first explain why it is necessary and whether it can be avoided.

Prefer deletion and simplification over adding complexity.

# 3. TECHNOLOGY STACK

Use the following lightweight architecture unless there is a strong technical reason not to.

## Frontend

* React
* Vite
* TypeScript
* CSS or a lightweight styling approach
* React Router only where routing is actually needed
* Recharts or another lightweight charting library ONLY for the required reports

Avoid unnecessarily large UI frameworks.

## Backend

* Python
* FastAPI
* SQLAlchemy

## Database

Start with:

* SQLite

SQLite is intentionally preferred because this is an academic demonstration system and does not require a large distributed database.

Use PostgreSQL only if there is a clearly demonstrated requirement that SQLite cannot satisfy.

## AI recommendation engine

Do NOT make every recommendation request call an external generative AI API.

Implement the recommendation engine locally using a lightweight recommendation/scoring algorithm.

The recommendation engine should use available information such as:

* product category
* product characteristics
* customer purchase history
* products viewed/selected where available
* eco score
* carbon impact

A simple weighted recommendation score is preferable to a computationally expensive model.

For example:

recommendation_score =
relevance_score * 0.4
+ category_similarity * 0.3
+ sustainability_score * 0.3

Adjust the formula if a better simple approach is appropriate.

The recommendation algorithm must be explainable.

## B. Eco-friendly alternatives

If the selected product has a greener alternative, recommend it.

```text

Reusable Stainless Steel Bottle

Reason:
Similar product category with a higher eco score
and lower estimated carbon impact.
```

Recommendations should include an explanation.

Do not pretend the recommendation engine is using advanced machine learning if it is actually a scoring algorithm.

If later an actual ML model is useful, it can be introduced as an optional enhancement, but do not make it necessary for the first working version.

# 11. GREEN DELIVERY

Create several delivery options with simple environmental characteristics.

Example:

```text
Standard Delivery
Eco Delivery
Express Delivery
```

Each delivery method should have:

```text
delivery speed
delivery cost
emission factor
```

The system should estimate delivery emissions.

Example conceptual calculation:

```text
delivery_carbon =
distance × package_weight × emission_factor
```

Use clearly documented assumptions.

The system must recommend the greener option.

Example:

```text
Recommended:
Eco Delivery

Reason:
Lower estimated carbon impact than Express Delivery.
```

The recommendation should not simply select the cheapest option.

# 12. CARBON FOOTPRINT ESTIMATOR

Implement a transparent estimation system.

Calculate:

```text
Product Carbon Impact
+
Delivery Carbon Impact
=
Estimated Order Carbon Impact
```

Display the result to the customer before order submission.

Example:

```text
Estimated Environmental Impact

Products:       1.80 kg CO₂e
Delivery:       0.70 kg CO₂e
-----------------------------
Total:          2.50 kg CO₂e
```

Use the unit:

```text
kg CO₂e
```

Clearly label values as **estimates**.

Do not make unsupported claims about exact real-world emissions.

Store the calculated value with the order so it can later be used for sustainability reporting.

# 17. API EFFICIENCY

Minimize API requests.

Use:

* Pagination
* Appropriate endpoint design
* Response data limited to what the screen needs
* Client-side reuse/caching of data where appropriate
* No unnecessary polling
* No repeated API calls caused by frontend rendering

Before implementing an endpoint, ask:

> Does this request need to happen, and can the required information already be available?

Avoid endpoints that exist only because they are conventional.

---

# 18. FRONTEND RESOURCE EFFICIENCY

Optimize:

* Bundle size
* Images
* API requests
* Re-renders
* Component loading
* Network requests

Do not install a large library when a few lines of code can solve the problem.

Compress/resize product images.

Avoid auto-refreshing dashboards.

---

# 19. AI RESOURCE EFFICIENCY

AI must NOT become the largest consumer of resources.

Do not call an external LLM for:

* Simple product similarity
* Carbon calculations
* Delivery calculations
* Inventory thresholds
* Reports

These should be deterministic algorithms.

Use AI only where it actually contributes to the required recommendation functionality.

Prefer:

```text
Local lightweight recommendation algorithm
```

over:

```text
External AI API request for every product view
```

If an external AI API is eventually used, cache recommendations and avoid repeated requests.

        ↓

    authenticate user
        ↓

# 2. EMAIL VERIFICATION CODE

Use a secure short-lived verification code.

* Codes must be single-use.

# 13. ORDER / INVENTORY BUG FIX

There is currently an inventory issue:

# 14. CANCELLATION BEHAVIOR

If an order is cancelled by:

* Customer
* Admin

then restore the ordered quantity to inventory if the quantity had already been deducted.

Example:

```text
Initial stock = 10

Customer buys 2

Successful payment
        ↓
Stock = 8

Order cancelled
        ↓
Stock = 10
```

If the order has not yet caused a stock deduction, do not subtract and then restore unnecessarily.

The inventory logic must be **transaction-safe and idempotent**.

Do not allow:

```text
Order delivered
 ↓
Stock decreases

Admin updates order again
 ↓
Stock decreases AGAIN
```

The stock must only be deducted once.

Likewise, cancellation should only restore stock once.
